# 工程护栏说明

> v1.0 原文，仅供参考：文中“SOP”＝现在的《交付规则》，“治理规范”＝《文档规则》，节号和 `<脚手架版本>` 占位已失效。

> 给人看的说明材料，不是规则。规则以 SOP 和代码里的检查配置为准。

## 总原则

**能让机器自动检查的，就不靠人看，也不靠写文档。** 把检查合成**一条全量命令**（类型检查、测试、代码风格等），跑完输出一页摘要；哪一步失败，就明确指出是哪一步，并让命令返回失败状态。

## 起步检查项

下面的数字只是示例默认值，项目按自己的情况调。

| 检查 | 防什么 | 示例阈值 |
|---|---|---|
| 单文件行数上限 | 巨型文件 | 400 行 |
| 函数长度上限 | 看不懂的长函数 | 80 行 |
| 嵌套层数上限 | 层层嵌套 | 4 层 |
| 冗余代码 | 没人用的代码越堆越多 | 检查未被引用的文件、导出、依赖 |
| 重复代码 | 复制粘贴，改一处漏一处 | 重复率不上升 |
| 覆盖率不下降 | 新功能不带测试 | 设一个整数底线，只能升不能降 |
| 冒烟测试 | 常用功能被悄悄改坏 | 5 条核心用户路径 |
| 对抗测试清单 | 安全漏洞和极端情况 | 乱输入、断网、崩溃、恶意请求 |

- **已有的超标逐处登记为起点**，新代码守标准，已有的问题不能继续变大。
- 规则偶尔会误判。允许例外，但要写理由、由总控批准、留下记录。
- 覆盖率只是底线，高不等于功能正确；浏览器路径和异常数据，仍要单独验证。

## 如果远端 CI 能力有限

比如用的是免费版，重的检查（浏览器冒烟、覆盖率、重复代码）可以只在本机跑。这种情况下，可以考虑合并前把“远端测试结果”和“本机全量检查结果”都附上（建议；是否作为硬要求，要改 SOP 并走复核）。

## 怎么避免“修好这里，那里又坏”

下面都是**建议**，适用于已经有自动化测试的项目，不构成门槛；真正的硬要求只在 SOP 里。

1. 每个 bug 先写一个**复现测试**，修好后永久保留，同一个 bug 不会再回来。
2. 改动涉及共享部分或影响不明时，倾向多跑几类测试，不只跑相关的（具体跑多少按 SOP 第 8 节“按影响补验”判断，这里不加要求）。
3. 模块边界清晰，改动的影响范围小。
4. 修复时写明“可能影响哪些功能”，用户手测时重点看这些。
5. 尽量一次只修一个问题，出问题时好定位（建议，不是规则）。
