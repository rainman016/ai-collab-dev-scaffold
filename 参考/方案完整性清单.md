# 方案完整性清单

> v1.0 原文，仅供参考：文中“SOP”＝现在的《交付规则》，“治理规范”＝《文档规则》，节号和 `<脚手架版本>` 占位已失效。

> 说明材料里的“执行清单”（见治理规范第 9 节的例外）：产品经理出方案时逐项过一遍，每项写“怎么处理”，或“不涉及＋理由”。内容只限检查提问，不写授权、门禁或禁止。手测或事故暴露出新遗漏，由总控归类补成提问，不需要规则复核。

## 一、七维检查

| 维度 | 要回答的问题 |
|---|---|
| 角色 | 谁用？谁管？不同角色看到什么、能做什么？个人、负责人、管理员用的是同一个业务口径吗？ |
| 入口 | 从哪里进来（菜单、跳转、角标、通知、接口）？完成后去哪？怎么返回？同一个能力有几个入口，每个入口的结果一致吗？ |
| 数据 | 来源、筛选口径、更新频率和更新时间、失败后怎么重试？前后口径一致吗（推荐从哪儿来，命中就查哪儿）？写入、删除能撤销或恢复吗？有没有内容发给外部？ |
| 规则 | 筛选、推荐、排序怎么算？用到模型的：“好”的标准是什么？拿多少样本评、及格线多少？出错或没结果时怎么兜底？调用次数、费用、等待时长？ |
| 状态 | 首次使用、数据多、数据少、无结果、出错、加载中、内容超长或数量极端，各显示什么、给什么操作？ |
| 异常 | 中途离开、刷新、重复点击、撤销、超时、结果不确定（请求发出了但没拿到明确结果），各怎么处理？ |
| 兼容 | 旧数据、旧入口、旧的查询和统计会被新功能误伤吗？和其他模块（设置、列表、联动页面）怎么分工、不重复？ |

再加一项：**验收**——每条按“前提 → 操作 → 结果”写，含真实数据的场景；用到模型的，另有效果验收。

没有界面的项目：“入口”看接口和调用方，“状态”看返回值和空值。

## 二、交稿前的三项自查

1. **场景走查**：用真实数据，把用户典型的一天走一遍（打开 → 看到什么 → 点哪里 → 去哪 → 回来）。卡住、找不到入口、需要猜的地方，就是遗漏。
2. **事前预演**：假设这版手测不通过，写出最可能的 3 个原因，先处理掉再交。
3. **视觉自查**（有界面时）：截图后眯着眼看，只有主区块最突出；再按项目的视觉规范逐项单独判断，不笼统地说“看着还行”。
