# 问题卡索引

> 说明材料，不是规则。像路由一样用：**出了问题或返了工，先找关键词，只翻匹配的那一张，不通读全部。**

## 怎么用

```text
发现风险／失败／返工 → 找关键词 → 翻匹配的问题卡 → 照卡自问和检查
→ 优先把防法固化到代码、自动测试或仓库机制里
```

问题卡只给通用的方法，不记录某个具体任务的状态、计数或结论；具体状态放在任务的当前状态里。

## 起步 4 张

| 关键词／什么时候翻 | 问题卡 | 解决什么 |
|---|---|---|
| 复核了好几轮还在漏、提交后才冒出本该提前发现的缺陷、测试很多但没测到点子上 | `复核与验证遗漏.md` | 复核盲区、反例测试、验证绑定同一个版本 |
| 用了队列／重试／外部服务，请求发出去了却没拿到明确结果 | `异步与外部结果不确定.md` | 结果不确定、幂等、恢复、对账 |
| 同一个能力有多个入口或多种角色，改了一处别处没跟上 | `多入口不一致.md` | 角色、入口、数据口径、统计、删除的一致 |
| 接手要读一大堆历史、同一状态写在好几处、分支越开越多 | `上下文与文档失控.md` | 单一状态源、分支收敛、渐进读取 |

## 什么时候新增或更新一张卡

先判断这个问题是：已有规则没被执行？只是本项目的专项问题？还是别的项目也会遇到的通用缺口？

只有同时满足下面两点，才新增或更新问题卡：

1. 没有更合适的落点——不能靠代码、自动测试、仓库已有的机制来防；
2. 值得占一张卡的理由，至少有一条：
   - 这类问题复发了（同类出现两次以上）；
   - 后果严重——一次就可能伤到权限、钱、数据或线上安全；
   - 波及面广——不止一个功能、入口或角色会中招；
   - 现有的复核流程反复漏掉它；
   - 你手上有可复现的证据，证明问题真实、做法管用。

普通的工程方法，经独立验证后可以直接更新；涉及产品、权限、计费、生产或验证门槛变化的，要用户确认。

## 什么时候退出

问题已经被公共代码、自动测试或仓库的正式机制稳定防住，就从索引里拿掉；历史证据留在原来的 PR 或任务记录里，不复制到这里。
