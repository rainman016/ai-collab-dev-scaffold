# AI 协同开发脚手架

*English: An AI-executed setup guide that turns a new or in-progress code project into a governed workspace — rules, folder layout, branches and approval gates — and then starts with an architecture review. It works on its own, or together with the companion "lead-session collaboration playbook" for multi-window AI work.*

> 版本 v1.0。与《总控协作手册》v3.x 衔接：多窗口怎么协作看那边，代码项目怎么交付看这里。《总控协作手册》尚未公开，公开后补链接。衔接细节见 [衔接说明.md](衔接说明.md)。

## 1. 一句话

开一个新代码项目，或者接手一个已经在做的项目时，把一份“搭建指令”交给 AI，它会把**规则、目录、分支、门禁**搭好，然后从“梳理项目架构”开始干活。

## 2. 它解决什么问题

用 AI 写代码时最常出的五类事：

| 问题 | 平时的样子 | 脚手架怎么防 |
|---|---|---|
| 代码写完就当完成 | AI 说“改好了”，一跑就坏；测试只覆盖了一部分，真实运行里的问题施工和检查都没发现 | 回报必须带版本号和证据路径，没亲自看过的写“未验证”；高风险改动由另一个会话独立复核 |
| 一句“可以”被当成推送许可 | 你说“可以”是同意方案，AI 理解成可以推上线 | 推送、合并、部署各有固定口令，一道一道单独说；“可以／继续／好的”都不算 |
| 几条线互相覆盖 | 两个 AI 同时改同一批文件，或者直接在正式目录里改 | 每条施工线一个文件夹、一条分支，登记后才开工；同时最多 2～3 条线，共享部分先合 |
| 换个窗口就忘了前面 | 新窗口从头翻聊天、重跑检查，上下文被截断 | 进度写在固定文件里，新窗口只读总览和当前状态就能接上 |
| 文档越写越多 | 规则、记录、过程文件堆成山，没人读完 | 一个事实只有一个主文件；任务收口时清过程文件；规则每月精简一次 |

## 3. 和另外两个包的关系

| 包 | 管什么 | 什么时候装 |
|---|---|---|
| 《总控协作手册》 | 多个 AI 窗口之间谁说了算：入口、派单、回报、通知、换窗接力、额度。**角色（岗位卡）只在这里定义** | 同时开 2 个以上 AI 窗口时 |
| **AI 协同开发脚手架（本包）** | 一个代码项目怎么交付：目录和分支、门禁、证据、复核、文档治理 | 有源码仓库的项目 |
| 《AI 协同 SOP 集》（规划中，尚未发布；发布后补链接） | 调研、可行性评估、UI 优化这类专项做法，全部标“草稿” | 需要时挑一份复制进项目，不装也能跑 |

- 三个都能单独用，也能一起用。一起用时规则冲突**以项目里的规则为准**——也就是本包在你项目里生成的那一份。
- 只装本包也行：一个 AI 窗口（Claude 或 Codex 都可以）当总控，另一个工具施工；没有另一个工具，就由总控兼任施工。“总控”就是你正在对话的那个窗口。

## 4. 怎么用

对 AI 说一句：“照 `搭建指令.md` 给这个项目搭结构。”它先判断是新项目还是已有项目。（如果你是 AI：接下来读 `搭建指令.md`，照它执行。）

### 新项目

1. **一次问完 9 个起步问题**，每个都带推荐答案，你只答一轮。本机没配 git 提交身份时多一条（名字和邮箱），AI 会在发问前先查，并进同一轮问，不会让你答两轮。
2. 按默认布局建好目录、规则和只读基线，**本地提交，不推送**。
3. 自动开出任务 01“项目架构梳理”。梳理完、你逐项确认后，才开第一条施工线。

| # | 起步问题 | 决定什么 |
|---|---|---|
| 1 | 项目名和英文简称 | 文件夹名、分支前缀 |
| 2 | 源码仓库已有还是新建 | clone 还是新建 |
| 3 | 技术栈和源码目录 | 任务 02 用什么检查命令 |
| 4 | 上线了没有、有没有登录、有没有持久数据（三项分别答） | 风险档：轻量还是完整（第 14 节） |
| 5 | 有没有另一个 AI 工具（如 Codex）来施工 | 没有就由总控兼任，复核另开独立会话 |
| 6 | 合并权在谁 | 个人模式还是团队模式（第 8 节） |
| 7 | 治理记录要不要推到一个私有备份仓库 | 治理区要不要配远端 |
| 8 | 会不会多窗口协作 | 会就提示一并装《总控协作手册》 |
| 9 | 本机有没有全局 AI 规则 | 合并不覆盖；门禁、授权、密钥这类硬规则照样写进项目（Codex 和别人的电脑读不到你的全局规则） |

### 已有项目（嫁接）

1. **只读盘点**：现有分支、工作树、PR、在途任务、已有规则和文档、CI 和仓库自带的规则。出一张盘点表给你确认。
2. **写位置映射表**：把现有路径对到第 5 节的四类位置上，**不搬、不改名**。
3. 在途任务登记进总览；旧文档登记进“主来源表”；和已有规则冲突的条目逐条列给你看。仓库自带的治理（CI、仓库里的 `AGENTS.md`、分支保护）**优先**，脚手架不覆盖。
4. 本地提交，开任务 01“现状架构梳理”：补齐产品边界、模块、数据主来源。

**嫁接改不改你的仓库**：不改。源码仓库里被版本管理的文件和仓库配置（hooks、分支保护、CI）一个不动，规则只放在治理区（治理区默认建在源码仓库外面，与仓库平级，不放进任何仓库里；你就在仓库里说“搭”时，AI 会给出建议位置让你确认）；新建施工分支和施工文件夹是正常施工，不算改。Codex 在施工文件夹里读不到治理区的规则，所以每份施工指令第一行都写“先读治理区的 `AGENTS.md`”。想撤回：按搭建时记下的“新增清单”，只删治理区新增的文件，再删掉 AI 自己新建的施工文件夹和分支（没合并的先问你）；你原有的笔记和后来写的代码都保留，不会整个文件夹删掉。这条“不改”只管搭建和嫁接阶段，规则生效后，已授权的任务在登记过的施工文件夹里正常改代码。

**规则从什么时候开始管用**：搭完后你说一句“确认规则生效”，AI 记下当时的提交号。在那之前，已有项目原有的工作照原来的做法（新规则下的施工线不开）；新项目只做搭建和任务 01（只读梳理、出方案），不开施工线。

## 5. 搭完长什么样

不管新项目还是已有项目，都分四类位置：

| 位置 | 放什么 | 规矩 |
|---|---|---|
| 治理区 | 规则、任务记录 | 只放文字，不放代码 |
| 正式工作区 | 源码仓库，固定检出 main、跟踪远端 main | 不在这里开发 |
| 施工区 | 每条施工线一个文件夹、一条分支 | 在总览登记后才施工 |
| 只读基线 | main 的一份只读副本 | 用来对照和跑基线，不改 |

**新项目的默认布局**：

```text
<项目根>/                     ← 治理区（本身是一个 git 仓库，只本地提交）
├─ AGENTS.md                  ← 路由和硬边界，首行写“开工先读本文件”
├─ CLAUDE.md                  ← 一行 @AGENTS.md（多窗口时再加总控规则导入）
├─ 项目文档/
│  ├─ AI协作偏好.md
│  ├─ 研发协作与交付SOP.md
│  ├─ 文档与上下文治理规范.md   ← 三份规范全文，轻量档限定默认读取范围
│  ├─ 工程手册/               ← 方案完整性清单、推送前扫描、护栏说明、复核结论模板
│  ├─ 问题卡/                 ← 索引＋4 张起步卡
│  ├─ 岗位卡/                 ← 4 张岗位卡副本（各带本项目补充）
│  └─ 任务记录/
│     ├─ 当前任务总览.md      ← 施工区登记、数据库迁移版本号分配
│     ├─ 模板/                ← 施工指令、施工回报模板
│     ├─ 协作治理/当前状态.md ← 规则生效版本、脚手架版本、档位、模式、持续有效的授权
│     └─ 任务01 项目架构梳理/
├─ main/                      ← 正式工作区
└─ worktrees/<简称>-main/     ← 只读基线
```

文件名用中文，`AGENTS.md` 的启动句里写明“用 UTF-8 读”；源码仓库里不加文件，所以中文文件名只出现在治理区。只建有内容的文件，空目录用到时再建。为什么这样分，见 [docs/目录与分支.md](docs/目录与分支.md)。

**已有项目的映射表示例**（虚构项目“小卖部”，两个源码仓库、几十个平铺的工作树）：

| 位置 | 映射到 | 说明 |
|---|---|---|
| 治理区 | `<项目根>/shop-治理区`（新建，与两个源码仓库平级，不放进任何仓库） | 唯一新增的地方 |
| 正式工作区 | `<项目根>/shop-server/`、`<项目根>/shop-web/` | 两个源码仓库，各自固定 main |
| 施工区 | `<项目根>/wt-*`（已有，平铺） | 沿用现有命名，新线也照这个规律起名 |
| 只读基线 | 原来没有 → 在治理区下新建一个只读工作树 | 撤回时一并删除 |

## 6. 角色

**角色只在《总控协作手册》里定义**：一个总控，加 4 张岗位卡——需求分析师、产品经理、开发工程师、质量评审。本包不另起炉灶，只补代码项目特有的部分：

| 角色 | 本包补什么 |
|---|---|
| 总控 | 代码项目里的“状态”就是当前任务总览＋任务当前状态；门禁口令由总控执行。总控可以是 Claude，也可以是 Codex（工具名对照见手册的平台适配） |
| 产品经理 | 方案五步＋方案完整性清单（含影响面七维，第 7 节） |
| 开发工程师 | 施工区和分支规则；施工指令、施工回报的固定结构和停止条件 |
| 质量评审 | 必须独立复核的改动清单；复核者不能是实施者 |

- 只装本包时，岗位卡随包附一份副本，注明来自手册哪个版本。
- 没有另一个施工工具：总控兼任施工，同样在施工文件夹里做；复核另开一个独立会话。

## 7. 一件事怎么走

```text
阶段识别 → 交付约定 → 定档 → 方案 → 施工指令 → 施工 → 回报 → 验收与复核 → 门禁 → 收口
```

**先看现在最主要的未知是什么**（阶段识别）：

| 现在最不清楚的 | 走哪条线 |
|---|---|
| 目标还没定 | 探索收敛：先把“要什么”说清 |
| 事实不清楚 | 调研，只读评估 |
| 不确定值不值得做 | 可行性评估，只读评估 |
| 都清楚了 | 进入施工 |

需要专项方法时从《SOP 集》（规划中，尚未发布；发布后补链接）选一份装进 `项目文档/专项SOP/`，不装也能走“只读评估”。

**每一步做什么**：

| 步骤 | 做什么 |
|---|---|
| 交付约定 | 开工时把这件事的五项约定写下来：目标、范围（含不做什么）、完成条件、交付面、约束与授权。已经说清的不重复要 |
| 定档 | 事项分小／中／大三档，档越高要的方案和证据越多（注意：这和项目级的“轻量／完整”两档是两回事，见第 14 节） |
| 方案 | 产品经理按五步出方案和验收标准（问题与价值、数据与效果、结构、可交互稿、验收标准），前一步经你确认才进下一步；对照方案完整性清单，影响面七维——角色、入口、数据、规则、状态、异常、兼容——逐项写“怎么处理”或“不涉及＋理由”。你确认后才施工 |
| 施工指令 | 总控写；施工方只认当前版本，聊天里的口头指令不算 |
| 施工 | 在登记过的施工文件夹和分支里做 |
| 回报 | 结论、版本、已验证（附路径）、未验证、失败项、待你定的事 |
| 验收与复核 | 按影响补验（第 9 节）；高风险改动另一个会话独立复核 |
| 门禁 | 第 8 节 |
| 收口 | 清过程文件；在总览记三个数：你拍板几次、返修几轮、越权或被推翻几次 |

交付约定五项、产品经理五步的细目、施工指令的固定内容，都在 `项目文档/研发协作与交付SOP.md`（模板在 `templates/项目文档/`）的第 3、5、6 节。

- **一个 PR 对应一个能单独验收、单独回滚的纵切**。
- **返修最多 2 轮**；到第 3 轮先停下，查是规则没执行、规则不够，还是一次性问题。

## 8. 门禁：个人模式与团队模式

门禁就是“不可逆的动作，每一道都要你单独说一句口令”。“可以／继续／好的”都不算。口令由总控执行，其他窗口不执行。

先看你属于哪种模式——**模式定“谁签哪道门”，档位（第 14 节）定“门有几道、查得多严”**，两件事互不影响。

### 两种模式的区别

| | 个人模式 | 团队模式 |
|---|---|---|
| 仓库归谁 | 你自己 | 团队或组织 |
| 谁能合进 main | 你说口令后，由总控合 | 只有仓库负责人，按仓库自己的流程 |
| 你要做的 | 手测，加每道门禁的口令 | 手测，加一句“确认发布候选” |
| 之后谁管 | 你 | 仓库负责人：完整 CI、正式验收、合并、发布 |
| AI 能不能合并、推 main | 能，但每道都要你的口令 | 不能 |

**怎么选**：只有你能往 main 合 → 个人模式；main 有分支保护、要别人审批，或者仓库属于团队或组织 → 团队模式。拿不准就选团队模式（AI 权限更小，更保守）。

### 个人模式：完整档六道

| # | 门禁 | 谁签 | 口令 | 签了之后发生什么 |
|---|---|---|---|---|
| 1 | 自动验证 | AI 自己跑 | — | 全量检查命令通过，结果附路径 |
| 2 | 手测 | 你 | 说手测结果 | 你按验收标准实际试过 |
| 3 | 发布候选 | 你 | “确认发布候选” | 定下要合进 main 的那一版 |
| 4 | 合并到本地 main | 你 | “确认合并” | 合进本地 main，并在最新 main 上重跑自动验证 |
| 5 | 同步远端 main | 你 | “确认同步远端” | 推到远端 main |
| 6 | 部署 | 你 | “确认部署” | 上线 |

- 六道互不替代，说了后一道不等于前一道也签了。
- 走 PR 合并时，要同时有“确认合并”和“确认同步远端”两句。
- 远端是空的时候，首次接入远端的那一次授权（不论远端谁建）要写明含“推送主线的空初始提交”（只有空提交、不含代码，推前照跑扫描），否则第一个 PR 没有目标主线；之后推候选、建 PR 照常，六道口令不变。

### 个人模式：轻量档四道

自动验证 → 手测 → 确认合并 → 确认同步远端。手测通过的那一版就是候选，不另说口令；没上线就没有部署这一道，要上线时先升到完整档。

### 团队模式

| # | 门禁 | 谁签 | 签了之后发生什么 |
|---|---|---|---|
| 1 | 自动验证 | AI 自己跑 | 同个人模式 |
| 2 | 手测 | 你 | 同个人模式 |
| 3 | 确认发布候选 | 你 | 总控推施工分支、建一个 Draft PR，备到可审 |
| 4 | 完整 CI、正式验收 | 仓库负责人 | 按仓库自己的规则 |
| 5 | 合并 | 仓库负责人 | — |
| 6 | 发布 | 仓库负责人 | — |

团队模式下没有“合并到本地 main”这一道；AI 不合并、不推 main。为什么这样设，见 [docs/六道门禁.md](docs/六道门禁.md)。

## 9. 证据与复核

- **基线什么时候对齐**：开工前对齐最新 main 并记下基线版本；施工中 main 有新合并，按影响决定要不要合进来；验收前确认候选是基于最新 main；合并后在最新 main 上重跑。
- **按影响补验**：候选版本变了，按改动影响补跑对应检查——不是一律全跑，也不是一律不跑。
- **检查结果复用**：引用以前跑过的结果，要写明那次的版本和环境；版本或环境变了就不能复用。
- **失败先分类**：产品问题、测试方法问题、环境问题，三类分开处理；同一原因重试通过，不算新证据。
- **必须独立复核的改动**：登录与权限、持久数据和数据库迁移、门禁类规则的修改等，清单在规则里写全；复核者不能是实施者。轻量档只有改门禁规则时才必须复核。

详见 [docs/证据补验与独立复核.md](docs/证据补验与独立复核.md)。

## 10. 并行与集成

- 同时最多几条线：完整档 3 条（其中一条专做集成），轻量档 2 条。
- 共享部分（公共组件、数据库迁移）先单独合并；迁移版本号由总览统一分配，不各自起号。
- 合并前先核对本地 main 和远端 main，远端有新东西先处理。
- 同步 main 用合并，不用变基；不改写 main 历史、不强推、不删远端分支。
- 合并后在最新 main 上重跑自动验证，再清理施工文件夹和登记。
- 小步合并；没做完的功能放在默认关闭的开关后面。
- 共用的运行资源（端口、测试环境）登记后再用，避免两条线同时跑撞车。

详见 [docs/并行与集成.md](docs/并行与集成.md)。

## 11. 文档与上下文

- **一个事实一个主文件**，别处只放链接。
- **读得少**：先读直接相关的，够用就停。
- **覆盖更新**：状态改原行，不往下追加流水账。
- **不建空文件**：用到时再建。
- **收口清理**：任务结束删过程文件，只留结论。
- **每月精简一次规则**。
- **问题卡**：出事时只翻对应的那张，不通读全部规则。起步带 4 张：复核与验证遗漏、异步与外部结果不确定、多入口不一致、上下文与文档失控。只有确实对多个任务有用的经验才升级成规则。
- **“不在 Git 里的东西”清单**：本地数据库、AI 记忆、证据目录等，换电脑时照单搬。

三份规范都有一段“核心规则（摘要）”，只用来定位；每份开头的“默认读取范围”才是必读范围：完整档读全文，轻量档读摘要加文件开头标注的章节，其余章节仍在文件里，进入对应环节再读（三份规范两档都是全文）。详见 [docs/文档治理.md](docs/文档治理.md)。

## 12. 规则本身怎么管

- **复制进项目，不引用原文件**：项目可以按自己情况改；脚手架更新了，不会悄悄改到你的项目。
- **记来源**：`协作治理/当前状态.md` 记脚手架版本、档位、个人／团队模式。
- **确认生效**：你说“确认规则生效”才生效，记下提交号。
- **完整档**：门禁类规则的修改，复核通过前不生效。
- **升级**：总控对照脚手架的 CHANGELOG 列出差异，你确认后再合进项目。
- **和本机全局规则的关系**：门禁、授权、证据、密钥这类硬规则总是写进项目；只有表达习惯（语言、回复长短、格式）可以写“见全局规则”；团队模式一律写全文。

详见 [docs/规则版本治理.md](docs/规则版本治理.md)。

## 13. 工程约束与护栏

- **工程实现四条约束**：不堆没依据的防御、入口校验内部流转、不提前抽象、控制复杂度。细则见 `项目文档/研发协作与交付SOP.md` 第 6.3 节。
- **任务 02 工程护栏**：有了源码之后，按技术栈建一条全量检查命令（类型检查、测试、代码风格等合成一条）和单文件行数上限；也可以并入第一条施工线，不单开任务。
- **推送前敏感扫描**：每类特征单独跑、看退出码；结果分清“扫了没命中”和“没跑成”，没跑成不算通过；同时扫文件内容和提交说明；有二进制文件时脚本停下，由你看过清单后才放行，AI 不得自行放行。

详见 [docs/工程约束与护栏.md](docs/工程约束与护栏.md)。

## 14. 两档对照

项目级分两档（轻量／完整），和第 7 节里单件事的“小／中／大”不是一回事。

| | 轻量档 | 完整档 |
|---|---|---|
| 什么时候用 | 上线、登录、持久数据三项都没有 | 三项里任何一项有，或拿不准 |
| 门禁（个人模式） | 4 道（第 8 节） | 6 道 |
| 独立复核 | 只有改门禁规则时 | 高风险改动清单里的全部要；走 PR |
| 同时几条线 | 最多 2 条 | 最多 3 条，一条专做集成 |
| 规则治理 | 说“确认规则生效”即生效 | 同左；另外门禁类修改复核前不生效 |
| 规则默认读取范围 | 核心规则摘要加文件开头标注的章节（三份规范仍是全文） | 全文 |
| 目录结构 | 相同 | 相同 |

**升档**：项目要上线，或加了登录、持久数据时，由总控提出，你确认后升。不自动升。

## 15. 怎么判断有没有用

分两层：做完时验一次能不能搭起来；用一段时间再看是不是真的少出事。

**第一层：搭建验收（脚手架做完就验）**

| 场景 | 通过标准 |
|---|---|
| 空文件夹搭一个虚构的新项目 | 你只答 1 轮问题；结构、本地提交、只读基线都建好；没有空文件 |
| 新开一个 Claude 窗口、一个 Codex 线程，只靠自动加载 | 都能答对：在哪施工、正式版在哪、要哪些口令、第一个任务是什么 |
| 嫁接到一个模拟的在途项目（平铺工作树、两个源码仓库、已有规则文件） | 已有分支、工作树、文件一个不搬不改名；在途任务全进盘点表；冲突条目全部列出；仓库自带规则没被覆盖 |
| 团队模式 | 生成的规则里 AI 没有合并和推 main 的权限，PR 交给仓库负责人 |
| 陌生人走查 | 一个只拿到仓库的独立 AI 照 README 搭一遍，卡住的地方为 0 |
| 私有信息 | 凭据和私有词扫描全历史 0 命中 |

**第二层：试运行（接入后跑够 3 件中档任务或 2 周，取先到者）**

| 看什么 | 通过标准 |
|---|---|
| 越权 | 没有口令的推送、合并、部署 0 次；“可以／继续”被当授权 0 次 |
| 说完成就真完成 | 回报说“通过”、事后被推翻 0 次；每份回报都有版本号和证据路径 |
| 派出去的事有人接 | 每次派单都有回执；停摆 4 小时内被发现 |
| 你不当传话筒 | 让你转述、复制指令 0 次；一件中档需求你拍板不超过 3 次 |
| 返修可控 | 同一问题返修超过 2 轮 0 次 |
| 换窗能接上 | 新窗口只读总览和当前状态就能继续，不翻聊天、不重跑已有检查 |
| 并行不撞车 | 两条线改同一批文件、共用资源撞车 0 次 |
| 文档不膨胀 | 规则文件字数比接入时增长不超过 20%；收口任务的过程文件已清理 |

收集：总控在每件任务收口时记三个数（第 7 节）；出事当场记一行。期满由一个独立 AI 读总览打分，总控不自评。全部通过算“有效”；越权或“说完成被推翻”出现任何一次就算“不通过”，先查原因再决定改不改规则。

没有现成的新项目时，先只做第一层；第二层等新项目开工再起算。团队模式只靠第一层的演练验证，除非试点本身是团队仓库。

## 16. 不包括什么

- 业务代码和技术栈模板（脚手架只管协作和交付，不替你选框架）。
- 推送、建远端仓库、部署的执行——脚手架只定门禁，执行要等你说口令，由总控做。
- 密钥：不读、不存、不生成。
- 专项做法（调研、可行性、UI 优化）：在《SOP 集》（规划中，尚未发布；发布后补链接）。
- 多窗口怎么协作：在《总控协作手册》。
