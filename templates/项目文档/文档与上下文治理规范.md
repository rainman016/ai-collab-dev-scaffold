# 文档与上下文治理规范

> 版本：<脚手架版本>。生效状态见 `任务记录/协作治理/当前状态.md`。
> 职责：规定事实放在哪个文件、AI 每次读多少、任务状态怎么记、文档什么时候建和删。**不复制**交付门禁（见《研发协作与交付SOP》）和协作表达（见《AI协作偏好》）。
> 默认读取范围：轻量档＝“核心规则摘要”＋第 1、2、3、4、7 节（其余节仍在本文件里，需要时再读）；完整档＝全文。

## 核心规则摘要（定位用；必读范围见文件开头“默认读取范围”）

1. **一个事实一个主来源**：别处只放链接或一句摘要。
2. **按任务加载**：只读完成当前任务所需的最少材料，不扫全部历史。
3. **稳定与动态分开**：入口文件 `AGENTS.md` 只放路由和硬边界；任务进度放当前状态和版本管理。
4. **当前状态覆盖更新**：不追加流水账；只在已核对的层面写“完成”。
5. **文档只在“有人要读、有人会更新”时才建**；被取代的先删重复，确有价值才归档。
6. **任务收口就清理**：只留结论，过程文件删掉。
7. **事实对不上，先确认读对了地方**，再找主来源，改实现和主来源到一致。
8. **说明材料不是规则**：工程手册不能偷偷加规则。

## 1. 核心原则

1. 一个事实，一个主来源。
2. 按任务加载，不把整个仓库当默认上下文。
3. 稳定与动态分离：长期规则进规范；`AGENTS.md` 只路由；任务进度留在版本管理、任务记录、当前会话。
4. 代码和文档同步：行为、接口、命令或边界变了，同一个任务里更新对应的主来源。文档不在源码仓库里时，在交付回执里写明两边各是什么状态。
5. 生成物不参与治理：依赖目录、缓存、构建输出、运行状态，不当事实来源，也不进版本管理。

## 2. 文档职责与主来源

搭建时按下表建好，“主来源”一列填项目的实际路径。

| 内容 | 主来源 | 说明 |
|---|---|---|
| 项目入口、当前能力、开发导航 | `<源码仓库>/README.md` | 正式状态以正式工作区为准 |
| 产品目标、范围、验收 | `<产品设计文档>` 和本任务的需求文档 | 目标不等于已实现 |
| 路由与硬边界 | `AGENTS.md` | 每次自动加载，必须精简 |
| AI 怎么理解、判断、表达 | `项目文档/AI协作偏好.md` | 不含工程流程和授权 |
| 研发推进与交付门禁 | `项目文档/研发协作与交付SOP.md` | 交付状态和授权的唯一主来源 |
| 文档放哪、读多少 | `项目文档/文档与上下文治理规范.md` | 本文件 |
| 给人看的说明材料 | `项目文档/工程手册/` | 不是规则，见第 9 节 |
| 跨会话任务的当前状态 | `项目文档/任务记录/<任务名>/当前状态.md` | 命中触发条件才建 |

| 部署、线上验证、回滚 | `<源码仓库>/docs/运行手册/` | |

## 3. 读取范围

**按任务读最少的材料**：

| 做什么 | 读什么 |
|---|---|
| 判断需求 | 当前任务目标和有效的需求文档；涉及整体边界再读产品设计 |
| 改页面 | 相关页面代码；涉及数据再读服务和存储 |
| 改接口或数据 | 服务端代码和相关存储、迁移 |
| 构建、部署 | 先读 SOP，再读部署手册 |
| 接续任务 | 当前状态、需求摘要、契约或 PR |

不为了解进度去扫全部历史、全部提交、全部聊天记录。

**默认不读也不沉淀**：依赖目录、缓存和构建输出；环境变量和密钥配置；完整的 AI 对话和思考过程；没筛选过的工具输出。需要诊断时，只取与问题直接相关的最小日志片段，临时日志不升级成正式文档。

`AGENTS.md` 只做路由和硬边界，不复制偏好、SOP 或治理细节。

## 4. 任务状态

### 4.1 什么时候建当前状态

满足任一条就在 `任务记录/<任务名>/当前状态.md` 建：

- 要跨会话或跨设备继续；
- 要跨会话验收，或要保存有效的候选版本和证据；
- 有阻塞、有并行依赖，或要别人接续；
- 用户要求长期跟踪。

一次性、单会话能做完的低风险小任务**不建**，由当前请求、分支和提交说明承载。内部步骤多，不是建状态文件的理由。任务总览只列“已经开工、正在推进或等收口”的事项，没开始的不预建目录、编号和队列。

### 4.2 怎么写

覆盖更新，不往下追加。固定六段：

```text
交付目标与范围：用户结果、做什么／不做什么、完成条件、交付面、有效来源
当前候选：唯一活动路径、分支、精确版本、未提交改动
有效验证：对应版本、场景、结果；分清自动验证、页面演练、手测、复核
剩余缺口：未完成项、待处理反馈（归属、影响、是否本批必修）、真实阻塞和解除条件
待授权事项：只列还缺的具体动作；已有授权保留其范围
唯一下一步：能继续做的动作，或确实要等的条件
```

写法：

- **只在已核对过的层面写“完成”**，没核对的写“未验证”。代码在不在主线、PR 开着还是关了、验收绑定哪个版本、有没有部署，是不同层面，不能用一个“已完成”概括。
- 不记测试计数、进程号、过期端口、命令流水、完整聊天摘要。
- 收口后按审计价值删除或归档。

### 4.3 反馈和口径怎么落

- 用户确认过的产品规则 → 需求文档或契约。
- 影响接续的最新口径、实现差异、未处理反馈 → 当前状态。
- 历史 → 版本管理。
- 用户纠正了旧理解，就直接更新有效口径，**不并存两套矛盾的方案**，也不把 AI 的建议记成“已确认需求”。
- 修好并核验过的反馈从“待处理”里移除；没做完的不能因为压缩状态而丢掉。
- 不按反馈轮次建记录、总结或授权台账。

### 4.4 需求摘要、变更契约、决策记录

**需求摘要**：范围要先冻结、但没到契约级别时，写在当前状态或 PR 里：目标、非目标、用户场景、拟改的规则、影响面、完成标准、未决项。

**变更契约**：命中下面任一项，在任务分支写 `docs/变更契约/<名>.md`（目标、边界、验收、风险、回退）：

- 登录、身份、权限、跨账号数据；
- 同步凭证、重要数据的生命周期、删除和恢复；
- 数据库结构、迁移、不可逆变更；
- 异步状态、重试、幂等、恢复；
- 公开接口或外部系统约定；
- 修改 CI、安全、验收、发布门禁。

契约进入施工后**冻结语义**。要改，先按 SOP 确认范围，再在原文里记：修订版本、原因、替代范围、生效条件，保留旧版本可追溯。不静默改历史结论。

**决策记录**：改变产品边界、数据安全、权限模型、跨模块接口或数据模型，或者有多个合理方案、取舍会影响后续维护时，记一条：背景、选择、主要取舍、替代方案、状态、对应提交。聊天记录不能当唯一的决策来源。

## 5. 新建、更新、归档、收口

- **新建**：只有“需要跨会话长期保留、现有主来源装不下、能说出读者／用途／更新触发／退出条件”才新建；否则更新已有的。内部步骤、已授权动作、普通修复，不单独写计划、授权台账、总结。
- **更新**：产品范围、验收、接口、数据模型、配置、命令变了，必须更新对应主来源。AI 连续两次出现同样的误判，才考虑形成持久规则。
- **归档**：被新来源取代的文档，优先删掉重复内容；确有审计价值才归档，开头标明替代文档和失效日期。归档文件不出现在默认读取路径里。
- **任务收口清理**：任务按约定交付面收口后（交付面含合并、同步、退出施工区的，等这些动作做完），总控当轮收拢任务目录：
  1. 先确认目录里没有未提交的改动，有就停下问清归属；
  2. 当前状态覆盖成一段结论，写上最终版本号；
  3. 方案已校准进正式文档的删掉，没校准的只留最终版；
  4. 复核结论和交付回执（`交付回执.md`）各只留最终一份；
  5. 施工指令、回报、过程稿、演示稿删除；
  6. 历史靠版本管理，提交说明里列出删了什么。

  只装本包、没有独立总控窗口时，“总控”就是主会话。

## 6. 事实对不上时（冲突处理）

1. 确认当前分支、提交、环境，排除读错了目录。
2. 用测试或最小复现确认实际行为。
3. 按第 2 节的表，找到这类事实的主来源。
4. 代码偏离了已批准的产品边界时，不以“代码是新的”为由覆盖设计；先报告冲突，明确改哪一边。
5. 在同一次变更里把实现和主来源改一致，删掉重复的说明。

## 7. 接续与换窗

**接手顺序**：适用的规则 → 当前状态和当前任务单 → 实际的版本管理／PR／CI 和环境现场 → 当前待办要用的证据。

- 摘要只用来定位。授权、冲突、验收结论有疑问，回看原文；**摘要不是授权，也不是通过的证据**。
- 准备压缩上下文、换人、换窗口之前，先在安全停点更新当前状态。来不及写，恢复后第一步先核对版本管理、未提交的差异、服务状态，不把旧记录里的“干净”“运行中”当现状。
- 现场核实没变，就从下一步继续。换窗口、换模型本身，不触发重建环境、重复派工或整套重测。
- 同一份当前状态，同一时间只有一个人维护；换人先移交再改，不让多个窗口同时改。

## 8. 改进闭环与规则篇幅

- 不建机器可读的问题库，不建全量台账。
- 只有问题**复发**、涉及安全或数据风险、影响多个入口，或多轮复核仍遗漏，才形成规则候选。
- 固化顺序：公共代码或自动测试 → 正式契约或主来源 → 入口文件。已被代码或测试稳定防住的问题，不再占用默认上下文。
- 规则总字数定一个**软上限**；修订让总字数增加时，要写明同时删了什么，或净增的理由，由非实施者复核时一并判断。安全和授权底线不因篇幅被删。
- 每月提一次精简候选。

## 9. 工程手册与规则的边界

`项目文档/工程手册/` 是给人看的说明材料：

- 不约束执行，不计入规则篇幅，更新不需要规则复核；
- 和规则冲突时，以规则为准；
- **手册里不得新增或改变规则**；发现规则性内容，要搬进规则文件并走复核；
- 唯一例外：规则点名的执行清单（如方案完整性清单），要求逐项作答，内容只限“提问”，不写授权、门禁、禁止；补提问不需要规则复核。

## 10. 每次任务的治理检查

- **开始前**：确认目标工作区（基线工作区只读）、分支、最少读取范围。
- **交付前**：确认改的是正确的主来源；没有新增重复说明；没有纳入生成物和凭据；记了精确版本；没有越权发布、合并、同步或部署。

### 不在版本管理里的东西（换电脑时照单搬）

搭建时让用户填一张清单，至少包括下面五类，换电脑时逐项核对：

| 类别 | 例子 | 怎么搬 |
|---|---|---|
| 本地数据 | 本地数据库、会话库、上传的文件 | 先关闭程序再复制 |
| 验证证据 | 截图、日志、证据目录 | 可选 |
| AI 的记忆和配置 | 各 AI 工具的记忆文件、项目配置 | 按各工具自己的迁移说明 |
| 未推送的治理区 | 只有本地提交、没推到备份仓库的规则和任务记录 | 整个目录复制，或先推到私有备份 |
| 凭据和密钥 | 各种 Key、令牌、登录态 | **不复制**，新电脑重新申请或重新登录 |
