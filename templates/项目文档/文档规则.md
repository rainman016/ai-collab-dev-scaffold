# 文档规则

> 版本：<脚手架版本>。生效状态见 `任务记录/协作治理/当前状态.md`。
> 管什么：文档放哪、读多少、状态怎么写、怎么不膨胀。门禁和交付见《交付规则》；多窗口怎么协作见《总控协作手册》。

## 1. 三道闸：只准建固定几种文件

1. **只准建固定几种文件**：任务目录（名字必须以“任务”开头，体检只查这类目录）只放 `任务说明.md`、`当前状态.md`、`方案.md`、`施工指令.md`、`施工回报.md`、`复核结论.md`、`交付回执.md`（任务 01 另有产出 `架构梳理.md`）；清单外的先在当前状态写清谁读、谁更新、何时退出。
2. **提交时机器查**：`工程手册/文档体检.sh` 挂在治理区的提交关口（不碰源码仓库）。**拦**（退出码 1）：必读三件超限、硬规则关键句缺失、`AGENTS.md` 指到的文件不存在；**提醒**：其他文件超限、清单外文件、规则文件合计超软上限。退出码 2＝没跑成，算不通过。
3. **收口是一道门**：任务目录只剩最终文件、过程稿移进归档、体检通过，才能标“已交付”（见《交付规则》第 6 节）。

**上限**只放 `工程手册/文档上限.json`（一处，与手册重叠的键同名）。超限由写这份文件的人处理，**只能移走，不许删没处理完的反馈和授权**。归档只移不删，开头标“已失效，以某文件为准”，搜索不进归档，清理由用户定。加内容让规则文件超预算时，写明同时移走了什么，找用户调，不删硬规则。

## 2. 一个事实一个主来源

别处只放链接或一句摘要；事实对不上，先确认读对了地方，再找主来源，实现和主来源改到一致。

| 内容 | 主来源 |
|---|---|
| 路由、硬边界、检查命令 | `AGENTS.md`（每次自动加载，必须精简） |
| 交付状态与门禁 | 《交付规则》 |
| 现在做到哪、任务表、持续授权、施工区登记、迁移号 | 《当前任务总览》 |
| 某任务的进度 | 该任务的《当前状态》 |
| 产品目标、范围、验收 | `<产品设计文档>` 和本任务的需求文档 |
| 项目入口与开发导航 | `<源码仓库>/README.md` |
| 高风险变更契约（≤ 2,000 字） | 源码仓库 `docs/变更契约/<名>.md`，随代码审核 |
| 已定的项目决策 | 源码仓库 `docs/决策记录/` |
| 命令与实际行为 | 源码和配置本身，文档不复制命令 |
| 部署、线上验证、回滚 | `<源码仓库>/docs/运行手册/` |

生成物（依赖目录、缓存、构建输出、运行状态）不当事实来源，也不进版本管理。变更契约：登录权限、同步凭证、数据库结构和迁移、异步重试幂等、公开接口、CI 安全发布门禁，命中就写（目标、边界、验收、风险、回退）；进入施工后冻结语义，要改先确认范围，在原文记修订版本和原因，不静默改历史。

## 3. 读取范围

**按任务读最少的材料**，不为了解进度扫全部历史、提交和聊天记录。默认不读也不沉淀：依赖目录、缓存、构建输出、环境变量和密钥配置、完整对话和思考过程、没筛选过的工具输出；诊断只取最小日志片段。接续任务读：当前状态、需求摘要、契约或 PR。

## 4. 任务状态

满足任一条就在 `任务记录/<任务名>/当前状态.md` 建：要跨会话或跨设备继续；要保存候选版本和证据；有阻塞或并行依赖；用户要求长期跟踪。单会话能做完的小任务不建，不预建没开始的任务。

覆盖更新，不追加。固定六段：交付目标与范围｜当前候选（唯一活动路径、分支、精确版本、未提交改动）｜有效验证（版本、场景、结果）｜剩余缺口（未完成项、待处理反馈、阻塞）｜待授权事项｜唯一下一步。

- 只在已核对过的层面写“完成”，没核对的写“未验证”；代码在不在主线、PR 开着与否、验收绑定哪个版本、有没有部署是不同层面。
- 不记测试计数、进程号、过期端口、命令流水、聊天摘要。
- 用户确认过的规则 → 需求文档或契约；影响接续的最新口径和未处理反馈 → 当前状态；历史 → 版本管理。用户纠正了旧理解就更新有效口径，不并存两套方案，不把 AI 的建议记成“已确认”。修好并核验过的反馈才能从“待处理”移除。
- 总览“最近完成”超 10 行或满 7 天，行移进 `任务记录/归档/已交付记录.md`，不删（三个数是效果数据）。

## 5. 交接与换窗

交接只靠文件和 Git，不建 `HANDOFF.md`。接手顺序：适用的规则 → 总览和当前状态 → 实际的 Git／PR／环境现场 → 待办要用的证据。摘要只用来定位，**不是授权，也不是通过的证据**。换窗前在安全停点先改当前状态，再改总览“上一棒”；来不及写，恢复后先核对 Git、未提交差异和服务状态，不把旧记录里的“干净”“运行中”当现状。同一份当前状态同一时间只有一个人维护。

## 6. 新建、归档、改进

- **新建**文档要能说出读者、用途、更新触发、退出条件，否则更新已有的；内部步骤、已授权动作、普通修复不单独写计划或台账。
- **被取代的**先删重复，确有审计价值才归档，归档文件不进默认读取路径。
- **改进**只在问题复发、涉及安全或数据、影响多个入口、多轮复核仍遗漏时才形成规则；固化顺序：公共代码或自动测试 → 契约或主来源 → 入口文件。每月提一次精简候选。
- 说明材料（`工程手册/`）不是规则，不得新增或改变规则；发现规则性内容搬进规则文件并走复核。

## 7. 不在版本管理里的东西（换电脑时照单搬）

搭建后让用户补全《当前状态》第 4 节：本地数据（先关程序再复制）、验证证据（可选）、AI 的记忆和配置（按各工具的迁移说明）、未推送的治理区（整个目录复制或先推私有备份）、凭据和密钥（**不复制**，只写“有”）。**换电脑还要重挂治理区的提交关口**：钩子不进版本管理，在治理区 `.git/hooks/pre-commit` 写两行 `#!/bin/sh` 和 `bash 项目文档/工程手册/文档体检.sh || exit 1`（Mac／Linux 加执行权限），再手跑一次确认退出码 0。
