# 并行与集成

> 给想改规则的人看：为什么限制同时几条线、为什么共享部分先合、为什么用合并不用变基。具体规则在 `templates/项目文档/研发协作与交付SOP.md` 第 6.4 节。

## 规则是什么

- **条数**：完整档最多 3 条（其中一条专做集成），轻量档最多 2 条；调整上限要用户确认。
- **一线一夹一分支**，在《当前任务总览》的“施工区登记”写明文件夹、分支、任务、用途、状态、退出条件，没登记不施工。
- **共享部分先合**：公共组件、数据库迁移、公共路由等两条线都要碰的东西，先作为独立共享候选合进主线，各线同步后再用。
- **迁移版本号**由总览统一预先分配，施工线不自己起号。
- **合并前**核对本地主线和远端主线一致；**同步主线用合并，不用变基**；不改写主线历史、不强推、不删远端分支。
- **合并后**在最新主线上重跑自动验证，再退出施工文件夹并注销登记。
- **小步合并**：一个 PR 对应一个能单独验收、单独回滚的纵切；没做完的功能放在默认关闭的开关后面。
- **共用运行资源**（端口、测试环境）登记后再用。
- 产品范围冲突由用户定，技术冲突由总控定并记入任务记录。

## 为什么这样定

1. **并行的瓶颈是“集成”，不是“施工”**。AI 写得快，但每多一条线，合并时要处理的冲突、要重跑的验证都成倍增加。所以限制条数，并专门留一条线做集成。
2. **共享部分最容易冲突，也最难回头**。两条线各自改了同一个迁移或公共组件，合并时冲突往往是语义冲突，不是文本冲突。先单独合一次，后面的线在它之上继续，冲突就被提前消化了。
3. **迁移版本号集中分配**。各自起号会撞号，而数据库迁移撞号的后果比普通代码冲突严重得多。
4. **用合并，不用变基**。变基会改写分支历史，对已经发布、已被别人引用的分支是破坏性的；多个 AI 会话共享同一套分支时，改写历史会让别的会话的现场悄悄失效。
5. **小步合并**。大块改动在分支上存在越久，离主线越远，补验和冲突成本越高；每个纵切能单独回滚，出问题时不用连累别的功能。
6. **合并后重跑**。两条各自通过的线合在一起，不保证合在一起仍然通过。

## 不这样会出什么事

- 不限条数：十几条线同时在改，没人能说清主线现在包含什么，集成变成“撞大运”。
- 不先合共享部分：两条线各带一份不同的迁移，合并时数据库结构对不上。
- 用变基同步：已推送分支历史被改写，别的窗口引用的提交消失。
- 没登记就施工：总控不知道有这条线，退出清理时漏掉，施工文件夹和分支越积越多。

## 想改时要注意

- 想调高条数上限：要同时评估“集成线”和“复核”的容量；上限是用户确认项，不是 AI 可自行调整的数。
- 想改用变基：要先确认所有分支都只有一个人维护、且从未发布；否则不改。
- 想改版本号分配方式：迁移工具若自带版本机制，先确认它在并行分支上的行为，再改总览里的分配规则。
- 嫁接已有项目时，仓库自带的分支保护、CI 优先；本文规则不能覆盖它们。
