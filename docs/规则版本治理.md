# 规则版本治理

> 给想改规则的人看：规则为什么是“复制进项目”、怎么记来源、怎么升级、什么时候才算生效。相关记录在项目的 `任务记录/协作治理/当前状态.md`。

## 规则是什么

- **复制进项目，不引用原文件**：搭建时把模板复制成项目自己的规则，之后项目可以按自己的情况改。
- **记来源**：`协作治理/当前状态.md` 记脚手架版本、风险档（轻量／完整）、模式（个人／团队）、持续有效的授权。
- **确认生效**：用户说“确认规则生效”，AI 才算生效并记下提交号。在那之前，已有项目照原来的做法；新项目只做搭建和任务 01（只读梳理、出方案），不开施工线。
- **完整档**：门禁类规则的修改，复核通过前不生效。
- **升级**：总控对照脚手架的 CHANGELOG 列出差异，用户确认后再合进项目；不自动升级。
- **和本机全局规则的关系**：门禁、授权、证据、密钥这类硬规则总是写进项目；只有表达习惯（语言、回复长短、格式）可以写“见全局规则”；团队模式一律写全文。
- **升档**：项目要上线，或加了登录、持久数据时，总控提出，用户确认后才升，不自动升。

## 为什么这样定

1. **复制而不是引用**。引用意味着脚手架一更新，所有用它的项目的规则就在无人察觉的情况下变了；对一个靠“规则稳定”来约束 AI 的体系，这是最危险的事。复制让每个项目的规则变化都是一次显式的、可追溯的决定。
2. **记来源和版本**。以后升级时才知道“差在哪里”；出问题时也才能判断是规则版本过旧，还是规则本身不够。
3. **“确认生效”是一道门**。搭好的规则如果自动生效，用户可能还没看过就已经被它约束；让用户说一句话，等于把“知情同意”做实，并留下提交号作为现场。
4. **全局规则在别人那里读不到**。Codex 线程、团队里其他人的电脑，都读不到某个人本机的全局规则。如果“不读密钥”“口令才能推送”只写在全局，换一个执行者规则就消失了。所以硬规则必须写进项目，只有无关安全的表达习惯才允许引用全局。
5. **门禁类规则修改要复核**。规则是 AI 行为的边界，改规则的人和被规则约束的 AI 是同一个来源，必须有第三方看一眼。
6. **升档由用户确认**。档位决定门有几道，自动升降会让权限边界在用户不知情时变化。

## 不这样会出什么事

- 引用原文件：脚手架更新后，已搭好的项目规则被悄悄改，历史上的授权含义变了。
- 不记版本：几个月后没人知道项目用的是哪一版规则，升级无法对照。
- 搭完就生效：用户没读过的规则开始约束 AI，出现争议时无据可查。
- 硬规则只写全局：换个执行者（或换台电脑），红线就不存在了。

## 想改时要注意

- 想改“复制”为“引用”或“自动同步”：要先设计差异审阅和回滚；否则不改。
- 想改生效触发词：保持“需要用户主动说”这一点，不要改成 AI 自行判断。
- 想放宽“硬规则必须写进项目”：先逐条确认被放宽的规则在所有可能的执行者那里是否都读得到。
- 改了版本记录的字段，要同步改当前状态模板、CHANGELOG 的“升级时要对照什么”说明。
