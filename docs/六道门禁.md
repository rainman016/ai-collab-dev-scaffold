# 六道门禁

> 给想改规则的人看：门禁为什么这样设、为什么分两种模式和两档。具体规则在 `templates/项目文档/研发协作与交付SOP.md` 第 7 节（唯一主来源），这里不重复全文。

## 规则是什么

门禁就是“不可逆的动作，每一道都要用户单独说一句口令”。口令由总控执行，其他窗口不执行。

- **个人模式完整档六道**：自动验证（AI 自己跑）→ 手测 → 确认发布候选 → 确认合并 → 确认同步远端 → 确认部署。
- **个人模式轻量档四道**：自动验证 → 手测 → 确认合并 → 确认同步远端。
- **团队模式**：AI 只做到“确认发布候选”（推施工分支、建 Draft PR）；完整 CI、正式验收、合并、发布归仓库负责人，AI 不合并、不推主线。
- “可以／继续／好的／审核通过”都不算口令；六道互不替代。
- **首次接入远端**：建远端是外部动作，不在六道里。远端是空的时候没有主线，第一个 PR 没有目标，所以首次接入远端的那一次授权（不论远端由谁建）要写明含“推送主线的空初始提交”——只有空提交、不含代码，推前照跑扫描；之后推候选、建 PR 照常，六道口令不变。
- **模式决定谁签哪道门，档位决定门有几道、查得多严**，两件事互不影响。

## 为什么这样定

1. **“同意”和“授权”是两回事**。用户说“可以”，多半是在同意一个方案；AI 若把它理解成“可以推上线”，错误是不可逆的。固定口令加“一道一句”，把这两种意思彻底分开。
2. **按“能不能撤回”分道，而不是按流程阶段分**。本地合并可以撤销，推远端主线影响所有人，部署影响真实用户——三个动作的后果不同，所以不合并成一句话。走 PR 合并会直接更新远端主线，因此规定要同时有“合并”和“同步远端”两句。
3. **“工具能做”不等于“被授权”**。AI 的权限设置只说明它有能力，不说明用户同意。门禁写在规则里，不依赖工具的权限弹窗。
4. **团队模式把权限收小**。仓库属于团队时，合并权本来就不在个人手里；AI 若有合并能力，就越过了团队自己的审批。拿不准选团队模式，是因为误选“更保守”的代价只是多等一会儿，误选“更放开”的代价是越权。
5. **轻量档去掉“发布候选”和“部署”**。项目没上线、也没有登录和持久数据（三项都没有）时，影响面小：手测通过的那一版就是候选，没上线自然没有部署。想上线时先升到完整档，不是门禁自己悄悄多出一道。
6. **手测通过要用户明说**。用户主动免除的，记下范围和原因，不写成“通过”。
7. **空主线随首次接入远端一起授权**。备选做法是建远端后再单独说一次“确认同步远端”推空主线，更严，但多一道口令；因为空提交没有任何内容，不存在“偷带代码同步”，所以并进首次接入那次授权，口令一道不少、含义不变。

## 不这样会出什么事

- 只有一道“确认上线”：合并、推送、部署被一句话打包，用户无法只批准其中一步。
- 接受“可以／继续”：对话里的随口同意会被当成授权，事故后无法追责到“谁批的”。
- 团队模式里让 AI 合并：绕过仓库的分支保护和评审，团队负责人对主线失去控制。
- 把“自动验证通过”写成“可以发布”：测试覆盖不到的真实问题直接上线。

## 想改时要注意

- 想减少道数：先确认被去掉的那道所对应的动作是否仍然有人签，不能让某个不可逆动作变成“无人签”。
- 想新增口令措辞：口令要足够具体，不会在日常对话里被无意说出；并同步改 SOP 第 7 节、`AGENTS.md` 的硬边界、`衔接说明.md` 里的“门禁清单槽位”。
- 改门禁类规则本身属于“必须独立复核”的改动（完整档里复核通过前不生效），见《证据补验与独立复核》。
- 想让 AI 在某个范围内持续有授权，写成“已有授权在其范围内持续有效”的明确范围，不要放宽成“默认同意”。
