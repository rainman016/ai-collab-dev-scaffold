# 目录与分支

> 给想改规则的人看：为什么搭完是“四类位置”，施工为什么要一条线一个文件夹一条分支。搭建时不用读。具体规则在 `templates/项目文档/研发协作与交付SOP.md` 第 6.4 节。

## 规则是什么

项目里的位置分四类，职责不重叠：

| 位置 | 放什么 | 规矩 |
|---|---|---|
| 治理区 | 规则、任务记录 | 只放文字，不放代码 |
| 正式工作区 | 源码仓库，固定检出主线、跟踪远端主线 | 不在这里开发 |
| 施工区 | 每条施工线一个文件夹、一条分支 | 在总览登记后才施工 |
| 只读基线 | 主线的一份只读副本 | 用来对照和跑基线，不改 |

- 新项目用默认布局（见 README 第 5 节）；已有项目只写“位置映射表”，把现有路径对到这四类上，**不搬、不改名**。
- 施工区命名统一写成 `<简称>-<类型>-<简述>`（类型 `task`／`shared`／`link`，对应任务线、共享线、联动线），只用小写英文、数字、短横线；新项目里文件夹名与分支名相同，已有项目的文件夹和分支各自沿用原来的命名规律；已经发布的分支不为套命名而改名。
- 文件名用中文，入口文件 `AGENTS.md` 的启动句写明“用 UTF-8 读”；源码仓库里不加文件，所以中文文件名只出现在治理区。
- 只建有内容的文件，空目录用到时再建。

## 为什么这样定

1. **规则和代码分开放**。规则放在源码仓库里，每次改规则就变成一次代码提交，要跟着分支走、跟着合并走；而且团队仓库未必允许你往里加文件。放在独立的治理区，规则的版本和代码的版本互不牵连。
2. **正式工作区不开发**。它是“现在对外是什么样”的唯一参照。一旦有人在里面直接改，就没有“干净的主线”可以对照，也没法判断某个问题是基线自带的还是新改出来的。
3. **一条线一个文件夹一条分支，登记后才开工**。AI 同时干活时，最常见的事故是两条线改了同一批文件，或者在错误的目录里改。物理隔离加登记，让“谁在哪改什么”能被一眼查清。
4. **只读基线**。验收时需要一份和主线完全一致、没人动过的副本，用来跑“改动前”的结果、核对“这个问题以前就有吗”。
5. **嫁接不搬不改名**。已有项目有自己的历史和习惯，搬动路径会让在途分支、脚本、别人的肌肉记忆一起失效；映射表的成本低得多，也方便撤回（删治理区新增文件，再删自己新建的施工文件夹和分支）。治理区默认建在源码仓库外面（与仓库平级的上一级目录），不放进任何源码仓库：放进去会多出未跟踪目录和嵌套仓库，等于改了源码仓库。
6. **中文文件名**。读规则的主要是说中文的用户，文件名一眼能懂比“看起来规范”更重要；风险（编码）用启动句和“不进源码仓库”两道限制住。

## 不这样会出什么事

- 规则放进源码仓库：规则修改和业务提交混在一起，团队仓库的评审被无关改动淹没；撤回脚手架要改源码历史。
- 在正式工作区直接开发：主线和工作现场分不清，“基于最新主线”无法核实。
- 没登记就开工：两条线撞同一批文件，要到合并时才发现。
- 嫁接时搬目录：在途任务的路径失效，别人的工作被打断。

## 想改时要注意

- 改“四类位置”的数量或职责，会连带影响施工区登记、基线刷新、退出清理三处规则，要一起改。
- 想把规则放回源码仓库的，先确认三件事：仓库归谁、主线有没有保护、Codex 等施工工具在施工文件夹里能不能读到治理区（读不到，所以每份施工指令第一行都写“先读治理区的 `AGENTS.md`”）。
- 想改文件名为英文的，要同步改 `AGENTS.md` 的路由表、模板里的互相引用、`衔接说明.md`。
- 搭建／嫁接阶段“不改源码仓库被版本管理的文件和仓库配置”是脚手架对用户的一条承诺（撤回成本低），放宽它要重新向用户确认；它只管搭建本身，规则生效后在登记过的施工区正常改代码不受此限。
