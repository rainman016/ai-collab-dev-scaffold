# 证据补验与独立复核

> 给想改规则的人看：为什么“版本号加证据路径”，候选变了怎么补验，哪些改动必须另一个会话来复核。具体规则在 `templates/项目文档/研发协作与交付SOP.md` 第 8、9 节，复核结论模板在 `templates/项目文档/工程手册/复核结论模板.md`。

## 规则是什么

- **回报只认文件**：写结论、版本、已验证（附证据路径）、未验证、失败项、待用户决定的事。没亲自看过的写“未验证”。
- **基线对齐**：开工前、交用户验收前、交付前分别核对一次目标分支；施工中只有相关依赖或契约变了才检查。无法核实的状态不能写成“已对齐”。
- **候选变了，先看完整差异，再按实际影响补验**：
  - 行为和契约都不变（文档、测试、无引用文件清理）：记下依据，原结论可继承。
  - 局部路径变化：补验受影响的路径和必要回归。
  - 身份权限、迁移、删除恢复、关键依赖、安全、门禁类：扩大专项验证并复核。
  - 影响不明：先查清，不继承、不推进。
- **检查结果复用**：写明那次的版本和环境，核对代码、配置、依赖、数据、环境、命令没变；不能把旧结果写成“新版本实跑过”。
- **失败先分类**：产品问题、测试方法问题、环境问题；同一原因重试通过，不算新证据；不为了全绿删断言、跳过检查。
- **必须独立复核**：登录与权限、持久数据与迁移、公开接口与外部依赖、门禁类规则的修改、用户指定的高风险变更。复核者不能是实施者，只看完整差异和证据，不看实施者的自评。轻量档只有改门禁规则时必须复核。

## 为什么这样定

1. **AI 的“完成”常常只是“我改完了”**。把“完成”拆成可核对的三样（版本、证据、没验证的部分），后来者才能判断能不能信、该补什么。
2. **“不是一律全跑，也不是一律不跑”**。全跑成本高、会让人干脆不跑；一律不跑会让变了的东西带着旧结论上线。按影响分档，是在成本和风险之间找一个能被检查的中间点。
3. **“冲突解决成功”不等于“证据仍然有效”**。合并引入的新差异、基点变化，可能让之前的测试结论失效，所以要看差异而不是看合并有没有报错。
4. **重试通过不算新证据**。偶发失败被重试“洗白”后，真正的缺陷（竞态、环境依赖）会被埋住。分类能让人知道该改产品、改测试方法，还是修环境。
5. **复核者不能是实施者**。人（和 AI）都倾向于认为自己的改动没问题；只看差异和证据、不看实施者的推理，才能保证复核是一次独立的判断。
6. **高风险清单只增不减**。这几类（身份、数据、公开接口、门禁）出错的代价不对称：一次出错可能无法回退，所以宁可多复核。

## 不这样会出什么事

- 回报只写“通过”：事后被推翻时，找不到是哪个版本、哪个环境、跑了什么。
- 候选变了仍沿用旧手测：改了权限逻辑却说“之前测过”。
- 实施者自己复核：同一个盲点看两遍，结论等于没复核。
- 把“局部测试通过”当整体通过：没覆盖到的路径在线上出问题。

## 想改时要注意

- 项目里不能减“必须复核”的清单，只能加；本条不是给项目减项的授权。想改的是脚手架上游规则本身（把某一类从清单里拿掉）时，要写明去掉哪一类、为什么这类的风险已被别的机制覆盖（如自动测试、契约冻结），并经独立评审、随新版本发布；已搭好的项目要等升级时由用户确认，不能自行删项。
- 想改“版本号加证据路径”的格式：要同步改回报模板、施工指令固定结构、复核结论模板。
- 想让复核者“看实施者说明”：这会破坏独立性；若确实需要背景，只给契约和需求摘要，不给推理过程。
- 只装脚手架、没有第二个 AI 工具时，复核者可以是另开的独立会话；不能是同一会话“换个角度再看一遍”。
