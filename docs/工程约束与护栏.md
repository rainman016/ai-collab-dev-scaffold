# 工程约束与护栏

> 给想改规则的人看：为什么有“四条工程实现约束”、为什么要一条全量检查命令、为什么推送前扫描要写得这么死。约束本身在 `templates/项目文档/研发协作与交付SOP.md` 第 6.3 节；护栏和扫描的说明材料在 `templates/项目文档/工程手册/`（护栏说明、推送前扫描）。

## 规则是什么

**工程实现四条约束**（SOP 6.3，是规则）：

1. 不堆没有现实依据的防御；确要为低概率场景加复杂机制，先说触发条件、可能性和成本。
2. 外部数据在信任边界校验一次，内部按约定流转，不每一层重复校验。
3. 不提前抽象；只用一次的逻辑就近写。
4. 控制复杂度：只在能处理或补充上下文的位置捕获异常，不静默吞错。

**工程护栏**（说明材料，数值是示例默认值）：有了源码后，按技术栈建**一条全量检查命令**（类型检查、测试、代码风格等合成一条）和单文件行数等上限；已有的超标逐处登记为起点，新代码守标准。

**推送前敏感扫描**：每类凭据特征单独跑、看退出码；先自检；只输出文件名；“扫了没命中”和“没跑成”分开报告，没跑成不算通过。退出码：0 通过｜1 命中或有未确认的二进制｜2 没跑成或核对不一致；有二进制文件时由用户看过清单后才放行，AI 不得自行放行。

## 为什么这样定

1. **AI 倾向于“多写一点更稳”**。预防性防御、一层又一层的校验、为想象中的扩展提前抽象，都会让代码变长、变难读、变难改，而这些复杂度没有现实依据。四条约束是给 AI 的“刹车”，只约束“没有依据的复杂度”，不免除已知缺陷修复、安全、数据完整性和既有门禁。
2. **能让机器查的，不靠人看**。口头要求“文件别太长”“别重复”会被忘掉；写成一条命令，任何人和任何 AI 跑一次就知道是否达标，还能进持续集成。
3. **一条命令而不是多条**。多条命令会让人漏跑一条；合成一条并明确指出哪一步失败，门禁里的“自动验证”才有统一的含义。
4. **存量登记，增量守标**。现有项目一上来就要求全部达标是不现实的；登记起点、不让问题继续变大，既能落地又不放任。
5. **扫描写得死，是因为失败模式隐蔽**。“模式以 `-` 开头被当作选项而报错”和“某一类没跑成却被当成没命中”，都会让扫描看上去通过。所以：每类单独看退出码、出错一律不通过、先自检、只输出文件名（避免把凭据又打印一遍）。
6. **不按普通词扫**。按“密码”“Key”这类词扫会满屏误报，最后没人看；按凭据的格式特征扫，命中才有意义。

## 不这样会出什么事

- 没有约束：AI 在每个函数外包一层 try/catch、每层都重复校验，真正的错误被吞掉，排查变难。
- 没有统一命令：不同窗口各跑各的检查，“通过”的含义不一致。
- 要求存量立刻全部达标：规则被整体绕开。
- 扫描没跑成被当成通过：凭据被推到远端，且已被扫描“放行”。

## 想改时要注意

- 想加新的工程约束：先问它防的是什么具体事故、能不能用检查命令自动防住；能自动防的，不写成规则。
- 想改护栏阈值：示例数值只是默认；改项目里的数值不需要改规则，但要写明依据，例外要有理由并由总控批准。
- 想改扫描：保持“每类单独、看退出码、出错不通过、先自检”这四点；增加特征时同样先自检。
- 覆盖率只是底线，高不等于功能正确，不要把它写成验收标准。
- 约束的适用范围是“没依据的复杂度”；不要扩写成“禁止异常处理”或“禁止抽象”。
